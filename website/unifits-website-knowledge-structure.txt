useModal (src/hooks/useModal.ts)
  Reusable modal state manager. Generic: useModal<T>()
  Returns: { isOpen, data: T | null, open(payload: T), close(), toggle() }
  open(item) sets data=item so the modal knows which row was clicked.
  close() clears data to null.
  Usage:
    const modal = useModal<User>()
    <button onClick={() => modal.open(row)}>View</button>
    <InfoModal open={modal.isOpen} onClose={modal.close}>
      {modal.data && <DetailPanel item={modal.data} />}
    </InfoModal>

Login flow (mock):
  LoginForm.tsx matches credentials against MOCK_USERS.
  Success → calls handleLogin(user: User) in App.tsx.
  App.tsx writes sessionStorage: 'unifits_authed'='true',
    'unifits_user'=JSON.stringify(user).
  On page refresh: sessionStorage restored → auto-login.

Auth guard in App.tsx:
  auth:false routes (/login, /forgot-password) → visible when signed out;
    a signed-in user is redirected to /dashboard.
  All other routes → require authed=true.
  Unauthenticated → redirect to /login.

currentUser prop:
  App.tsx passes currentUser (User | null) to every page.
  Use: currentUser.id, currentUser.role, currentUser.full_name.
  Pages receive it as a prop — never read from sessionStorage directly.

Logout:
  Header triggers ResponseModal (warning variant) for confirmation.
  Confirmed → setShowLogoutModal(false), call onLogout() from App.tsx.
  App.tsx clears sessionStorage, sets authed=false, navigates /login.

Real auth swap points:
  · handleLogin() in App.tsx → POST /api/auth/login
  · handleLogout() in App.tsx → POST /api/auth/logout
  · DEFAULT_ORG in App.tsx → GET /api/organizations/me
  · sessionStorage → optionally replace with httpOnly cookies

  1.13  MODAL SYSTEM RULES — DO NOT BREAK
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

InfoModal  → large content / detail / edit forms (max 920px, z:300)
ResponseModal → compact feedback only (max 460px, z:400)
Never mix the two. ResponseModal renders ABOVE InfoModal.

Animation contract (both modals follow this exactly):
  · CSS opacity + transform transitions ONLY — no @keyframe animations
  · `closing` boolean state + timerRef (useRef) drives the exit
  · 240ms exit duration
  · closingRef (useRef) prevents stale closure reads during fast toggles
  · ResponseModal also uses `snapshot` ref to freeze content during exit
  · Adding keyframe animations WILL cause flicker/reappear bugs

Scroll lock: useModalLock(open) hook in hooks/useModalLock.ts (used by InfoModal and
  ResponseModal; was an inline effect duplicated in both)
  · Sets body overflow:hidden + paddingRight = scrollbar width
  · Scrollbar compensation prevents page-width layout shift on open/close

CloseButton in InfoModal:
  · 32×32, solid dark bg (#374151), white X, border-radius 8
  · Hover: #111827 bg + standard lift effect
  · Always visible against any content color

        content -> body; created_by name string -> user id (name resolved); add image_url (optional).
    projects          -> Project                         -> MOCK_PROJECTS
        status loses 'rejected' (becomes approval_status); add approval_status, reviewed_by/at, rejection_reason;
        current_funding becomes DERIVED (view project_financials); created_by id.
    events            -> AppEvent                        -> MOCK_EVENTS
        same as projects, plus event_type (B-74); current_funding DERIVED (view event_financials).
    attendances       -> Attendance                      -> MOCK_ATTENDANCES
        user_name / activity (title) / recorded_by (name) -> ids: project_id OR event_id, recorded_by id (B-49).
        One row per person + activity + date.
    funds             -> Fund                            -> MOCK_FUNDS
        balance DERIVED (view fund_balances); remove currency (org currency applies); created_by id.
    payment_methods   -> PaymentMethodOption             -> MOCK_PAYMENT_METHODS
        PaymentMethod literal union -> string from the table (defaults: Cash, GCash, Bank Transfer, PayMaya, Cheque).
    utilities         -> Utility                         -> MOCK_UTILITIES
        Utility becomes the BILL: expense_type, total_amount, due_date (was payment_date), paid_to, notes, fund_id.
        amount_paid and status are DERIVED from approved payments (view utility_balances) -> they cannot contradict (B-19/B-78).
        MOCK_TRANSACTIONS needs matching category 'utility' payment rows so derived values equal today's numbers.
    transactions      -> Transaction                     -> MOCK_TRANSACTIONS (14 rows, all 'completed' today)
        fund (name) -> fund_id; payment_method (string) -> payment_method_id; user_name DERIVED; keep project_id/event_id;
        add utility_id, reviewed_by/at, rejection_reason; description + notes kept.
        EntryType gains refund, opening_balance; TransactionCategory gains utility; TransactionStatus -> pending/approved/rejected/voided.
    audit_logs        -> AuditLog                        -> MOCK_AUDIT_LOGS
        user (name string) -> user_id; add record_id, old/new values; actions gain approve/reject/void.
    backup_jobs       -> BackupJob                       -> MOCK_BACKUP_JOBS
        status gains 'pending'; trigger gains 'pre_update'; created_by -> id (null = System).
    settings, notifications -> no TS type yet (Settings page state; B-43 static notifications).
    sessions, login_attempts + auth columns on users -> AUTH: undecided, depends on the Supabase discussion.

  Rules the whole app must follow once implemented
    Direction: income, contribution, opening_balance = inflow (+); expense, refund = outflow (-). Amount is always > 0.
    Counted in balances/totals: APPROVED, not deleted. Pending, rejected and voided never count (B-27/B-35/B-39 family).
    Status mapping of today's data: completed -> approved, pending -> pending, failed -> rejected, cancelled -> voided.
    Project/event "funding raised" = contributions + external income (approved). Refunds on a project/event are
    OPEN: net_balance in the views subtracts them, current_funding does not — owner to confirm the definition.
    Approval: new project/event/transaction = pending. Reviewer needs approve_project / approve_event / approve_transaction;
    reviewing your OWN entry also needs approve_own_entries (DB trigger enforces it). Default roles (editable per org):
    Admin = all 37; Secretary = approve project/event + approve_own_entries, no approve_transaction; Treasurer =
    approve_transaction but NO approve_own_entries; Auditor read-only + audit logs; Member = view projects/events/announcements.
    Utility payments are ledger transactions (category utility, entry expense/refund) and need approval like any other.
    Dates: transaction_date, received_date, due_date, attendance_date are DATE (Manila day cannot shift).
    Money: NUMERIC(15,2) in the DB; the frontend keeps numbers (PHP).

  Not decided / for owner review
    1. Role names (President vs Admin) and the default permission sets above (assumptions, editable per org).
    2. Refunds in project/event funding (see Rules).
    3. Org-level fields the UI needs later: onboarding, org switching, subdomains are NOT part of this foundation.
    4. Overpaying a utility (payments > bill) is not blocked by the DB; the app must validate it.

  Implementation order (each step: failing test first, then tsc + eslint + build + full tests green)
    P1a types + mock data for transactions/funds/utilities, in small steps:
        1 status set pending/approved/rejected/voided ........ DONE
        2 fund by id (fund_id on transactions + utilities)
        3 fund balance derived (remove stored balance + currency)
        4 utility = bill; amount_paid/status derived from approved payment transactions
        5 payment method by id
    P1b projects/events (approval_status, event_type, derived funding) incl. B-74, B-71
    P1c attendance by ids (B-49); users/roles by id (B-21); announcements
    P1d B-01: pass record id via query param (#/employees/details?id=5); ROUTES table unchanged; "not found" state
    Then phases 2-7 of the agreed fix order. B-47 is fixed by batch 19 (belongsToItem matches by project_id/event_id) - included in this delivery.
    Items needing a backend are DISABLED until Supabase: Add* saving (B-66/B-78), Settings persistence (B-57),
    Wipe All Data (B-58), Import (B-23), live notifications (B-43). Real PDF export (B-37/B-51) comes after the bug fixes.
